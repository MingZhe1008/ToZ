# ToZ 开发需求文档

版本：v0.1 · 需求与交互设计稿  
编制日期：2026-10-20 · Windows 首版，预留 iOS  
产品主张：计划可以改变，开始值得被记住。

当前实现状态：Windows v0.2.1 安装版已交付，实际采用 Electron + Node 内建 SQLite + NSIS。安装、原生透明浮窗、托盘、自启动设置和双窗口持久化已接入。详细范围与使用方式见 [Windows 安装版说明](Windows安装版说明.md)。下文保留完整产品需求，不能据此认为独立子任务日期、工时、同步等后续能力均已交付。

## 1. 产品目标

为个人提供完全离线的日常待办工具。主客户端用于拆分、安排和回顾任务；桌面透明浮窗用于随时查看、完成和延期今日任务。最重要的是：任务延期后仍能看到最初何时开始、原本何时计划完成、改期过几次，以及每次改到哪一天。

本稿将“子集”理解为子任务；“每日待办”首先指每日任务视图，Windows v0.2.1 已支持按日、周、月、年自动生成独立周期实例。首版做 Windows，iOS 为后续独立交付，不在首版承诺跨端同步。

## 4. 日期与时长：不可混淆的业务规则

### 4.1 日期字段

| 字段 | 含义 | 修改规则 |
| --- | --- | --- |
| created_at | 任务创建的真实时刻 | 只写一次，UTC 时间戳 |
| initial_planned_date | 第一次设置的计划完成日期 | 首次非空时写入，后续改期不能覆盖 |
| first_started_at | 用户第一次执行“开始任务”的真实时刻 | 允许未开始时为空；第一次开始后锁定 |
| first_started_local_date | 首次开始时所在时区的日历日期 | 与首次开始一起保存，防止换时区改变起点 |
| first_started_timezone | 首次开始的 IANA 时区 | 随首次开始保存，例如 Asia/Shanghai |
| planned_date | 现在打算在哪天完成 | 允许修改，每次修改追加事件 |
| deadline_date | 可选的外部硬截止日 | 与计划日期独立；修改也记事件，不随延期联动 |
| completed_at | 最近一次完成时刻 | 完成时设置；重开后清空当前值，原完成事件保留 |

计划日期是“安排在哪天做完”，首次开始是“实际上哪天开始做”。新建不等于开始。若用户希望仅按创建日期统计，可另显示“已创建 N 天”，不要伪装为已开展工作。

如导入旧任务需指定历史开始日期，只在导入向导中允许，并记 `imported` 事件与原始来源。首版普通编辑页面不提供改写首次开始日期入口。所谓“不可篡改”是产品操作与数据库约束保证，不是对拥有本机数据库访问权的人提供防伪证据。

### 4.2 时长口径

- **持续天数**：开始日计第 1 天。开始后未完成：`max(0, localToday - first_started_local_date) + 1`；完成后以完成时在统计时区的日期为终点。统一在任务首次开始时区做日历日计算，不按毫秒除 24 小时。
- **未开始**：显示“尚未开始”，持续天数为空，不能显示“0 小时工作”。
- **暂停**：持续天数继续增加；它表示经过的日历时间。实际工时只统计投入记录。
- **重新打开**：保留首次开始，持续天数恢复计算，历史完成区间仍可查。
- **累计延期次数**：只统计 `rescheduled_later` 事件；同一天重复提交不产生事件。
- **净后移天数**：`max(0, planned_date - initial_planned_date)`。
- **累计后移天数**：每次向后改期的正增量求和；向前调整不会冲销累计值，另记 `rescheduled_earlier`。
- **实际投入**：手动工时日志的分钟数求和。父任务汇总自身与子任务工时，列表汇总不重复计入父子两份。

示例：10 月 12 日开始、最初计划 10 月 15 日完成，改为 17 日、19 日、20 日。截至 10 月 20 日为持续 9 天，延期 3 次，累计后移 5 天，净后移 5 天。实际投入多少小时只能由工时日志决定。

## 5. 核心流程

### 5.1 新建、开始与完成

1. 新建时分别选择计划开始和计划完成日期，默认今天；支持任意起止区间及 1 天 / 3 天 / 1 周 / 2 周快捷设置，可取消日期。完成不能早于开始。
2. 写入任务与创建事件，状态为 `todo`，首次开始为空。
3. 用户点击“开始任务”，写入首次开始信息并转为 `in_progress`；之后暂停/继续不重写起点。
4. 完成时写入完成事件与完成时间；允许从 `todo` 直接完成，此时不推测开始时间。
5. 子任务未完成时，阻止直接完成父任务，提示先处理子任务；不静默级联完成。
6. 所有子任务完成后提示父任务可完成，不自动完成父任务。
7. 重开已完成子任务时，若父任务已完成，必须在同一事务内重开父任务并分别记录事件。

### 5.2 延期与改期

1. 点击“调整计划”，展示当前日期、首次开始、最初计划与完整历史。
2. 若新日期晚于当前计划，标记为延期；若提前则标记为提前；无日期→有日期为排期，有日期→空为移除排期。
3. 当前无日期的任务不称为“延期”。快捷“明天”始终以本地今天为基准，若新日期早于当前计划需明确显示为提前调整。
4. 一次提交原子写入任务当前日期、事件和版本号；事件有幂等 ID，重复点击不会重复记账。
5. 延期原因可选。超过硬截止日只提示，不修改硬截止日；用户仍可保存新的计划。
6. 父子计划独立；延期父任务不自动延期子任务。子任务超出父任务计划时提示但允许保留。
7. 撤销通过追加反向事件恢复日期，保留原事件；不删除历史，统计中用 `reverted_by` 排除已撤销延期。
8. 跨日自动归入“以前遗留”，不得自动改日期、次数或首次开始。

### 5.3 今日视图与浮窗

- 今日待办集合：未完成且首次实际开始或计划开始不晚于今天，或计划完成已到期。未来截止的进行中任务也保留在今日。纯未来未开始任务进入即将到来；无计划且尚未开始的任务保留在全部任务。
- 已完成分组：`completed_at` 在本地今天，不依赖计划日期；当天完成的旧任务也能看到。
- 父子不重复计算进度：主进度以顶层任务为单位；单独展示有独立日期的子任务时标明父任务，保持固定去重规则。
- 浮窗展示今日与遗留。已开始或计划已开始的任务延期到未来后继续展示；完成后从待办轮播中移除。浮窗空白标题处双击展开 / 收缩，折叠时每 4 秒轮播今日未完成任务，滚轮切换、点击打开详情。
- 从浮窗打开详情，主客户端定位同一任务；两窗口操作都通过同一领域服务提交。
- 系统跨午夜、休眠唤醒、手动切换时区后重新计算今日集合，不生成自动延期事件。

## 6. 信息架构与界面

### 6.1 主客户端

三栏结构：左侧导航 / 中间待办 / 右侧详情。

- 导航：今天、即将到来、全部任务、延期记录、已完成、项目、数据与设置。
- 列表：日期、完成进度、快捷新建、检索；卡片显示标题、项目、持续天数、延期次数、子任务进度。
- 详情：标题与状态、首次开始（锁形标识）、最初计划、当前计划、外部截止、持续天数、投入、子任务、说明、事件时间线。
- 时间线：按操作时间倒序；延期项突出 `旧日期 → 新日期`、本次后移天数、原因和操作时间；可切换“全部 / 仅延期”。
- 月历：周一到周日七列，提供上月、下月与回到今天；每天最多展示 5 条，超过时显示剩余数量，展开后可收起。点击事项在侧边打开详情，点击日期新建该日待办。
- 月历按区间逐日展示同一个任务，起点优先取计划开始与首次实际开始中较早的日期；旧数据无计划开始时使用首次实际开始，否则使用计划完成日。未完成区间结束为计划完成、今天和起点中的最晚日期；完成区间止于实际完成日。延期延长区间，首次实际开始不变。每日仍最多显示 5 条，可展开；月任务总数按任务 ID 去重。未排期但已实际开始的任务也从开始日展示至今天。
- 日期选择器：新建与调整计划复用同一套灰白/蓝色交互日历组件，支持月份切换、今天、已选日期、键盘方向键与 Esc 关闭，避免系统原生日历与界面风格不一致。整体视觉依据用户提供的 macOS 截图，使用中性窗口、半透明材质和多彩项目标记。
- 延期记录：可跨任务检索，点击定位详情；统计次数与累计后移分别呈现。

### 6.1.1 甘特图

- 使用同一任务起止区间，按项目分组，可折叠。顶部日期和左侧任务列固定，支持横向 / 纵向滚动。
- 周 / 月时间尺度、前后导航、今天标线、任务天数、子任务进度；越界时间条裁剪，完整日期由提示保留。
- 项目 / 状态 / 关键词筛选；未排期入口和区间外定位；点击查看详情、完成 / 重开，排期通过已有弹窗提交并追加历史。
- 首版不含拖拽改期、任务依赖、负责人、基线。侧栏搜索可直接输入并检索全部任务，Ctrl+K 聚焦。

### 6.2 桌面透明窗口

- 默认宽 320、高 480 逻辑像素；范围宽 280–440，高 260–760；列表内部滚动。
- 顶部：拖动区域、今日日期、完成比例、置顶切换、折叠与打开客户端。
- 主体：任务标题最多两行，完成圆钮、延期入口、小号持续天数/延期次数。
- 底部：快速新增、透明度入口；空状态显示“今天已安排妥当”，可以继续新建。
- 面板背景透明度可调 35%–95%，文字不跟随整体降透明；模糊效果与透明度分开设置。
- 默认不置顶，用户可开启；默认不点击穿透。穿透开启后整窗不可交互，托盘和全局快捷键必须能恢复。
- 托盘菜单：显示主界面、显示/隐藏浮窗、解除穿透、备份、退出。
- 关闭主窗口默认收至托盘；退出必须退出两个窗口。浮窗隐藏后可通过托盘恢复。
- 保存显示器、位置、尺寸与透明度。显示器断开后夹回现有工作区；适配 100%/125%/150%/200% 缩放。
- “贴在桌面”和“置顶悬浮”是不同窗口行为。首版交付普通透明悬浮窗口，不承诺 Win+D 后仍保留或置于桌面图标后。

## 7. 数据结构与一致性

建议采用 SQLite，核心表如下。ID 使用 UUID，为后续导出和 iOS 数据交换准备稳定标识。

```text
tasks
  id, parent_id?, project_id?, title, description, priority
  status, created_at, updated_at, version, archived_at?
  initial_planned_date?, planned_date?, deadline_date?
  first_started_at?, first_started_local_date?, first_started_timezone?
  completed_at?, sort_order

task_events
  id, task_id, type, occurred_at_utc, timezone, local_date
  old_value_json, new_value_json, reason?, source_window
  operation_id UNIQUE, reverted_by?, schema_version

work_logs
  id, task_id, worked_on_date, duration_minutes, note?, created_at

projects / settings / schema_migrations
```

- `parent_id` 外键，不允许自引用与循环；首版只允许一层子任务。
- `first_started_at` 一旦非空，领域服务拒绝修改，SQLite 触发器提供第二道约束；其他两个起点字段同样锁定。
- `initial_planned_date` 从空变非空后锁定，不受清空当前排期影响。
- `UPDATE tasks … WHERE id=? AND version=?` 乐观并发；冲突刷新并提示，不静默覆盖另一窗口修改。
- 当前状态与事件在同一数据库事务内提交，失败则两者都回滚。
- Rust 核心独占写数据库，前端不能任意执行 SQL；事务成功后广播任务变更，窗口据版本增量刷新。
- 重命名、改说明也记事件；归档可恢复。首版不提供清空历史入口。
- 普通文件删除不是审计防伪方案；备份、导出、恢复必须保留完整事件。

## 8. 本地保存与备份

- 正式数据目录：系统应用数据目录下 `ToZ/`，含数据库、备份和日志，不写安装目录。
- 启动时检查数据库迁移与完整性；迁移前自动备份，失败保留旧库和错误信息。
- 每日首次有修改后生成一致性快照，保留最近 7 份日备份与 4 份周备份，可配置路径。
- 使用 SQLite Backup API 或等价一致性方法，不能直接复制正在写入的数据库主文件而忽略 WAL。
- JSON 全量导出含版本、任务、事件、项目、工时和时区；CSV 仅为人读报表，不能作为完整恢复格式。
- 恢复前预览任务和事件数量，自动备份当前库；非法格式、损坏文件、未知高版本必须拒绝。
- 备份失败显示持久提示与重试入口；磁盘满或事务失败不能显示“已保存”。
- 首版无登录、无遥测、无自动云同步；安装所需 WebView2 运行时应随离线安装方案提供或检测现有版本。

## 9. 技术方案建议

本节为初稿候选方案。Windows v0.1.0 实际采用 Electron + JavaScript 领域逻辑 + Node 内建 SQLite；下文 Rust 职责由 Electron 主进程承担，安全隔离通过 contextIsolation、受限 preload 和按窗口校验的 IPC 实现。后续技术取舍以安装版实现和移动端验证为依据。

建议 Tauri 2 + TypeScript 前端（可选 React）+ Rust 领域服务 + SQLite。它适合双窗口与本地存储；iOS 复用数据契约与领域规则的范围需在移动端技术验证后确定，不能直接承诺桌面窗口能力在手机复用。

主窗口与浮窗是两个独立 WebView。浮窗需原生开启 `transparent`、关闭边框，按用户设置置顶；点击穿透需原生窗口 API。仅设置 CSS `opacity` 或 `backdrop-filter` 无法让浏览器页面成为 Windows 系统浮窗。

官方能力参考：[Tauri 配置](https://v2.tauri.app/reference/config/)、[窗口 API](https://tauri.app/reference/javascript/api/namespacewindow/)、[窗口自定义](https://tauri.app/learn/window-customization/)。透明与 Windows 模糊材质需配合；不同 Windows 版本存在效果差异和拖动性能限制，必须先做样机验证，失败时降级为清晰的半透明底色。

首版基线建议 Windows 11 x64；Windows 10 若纳入交付，作为独立兼容目标验证透明、WebView2 与安装流程。iOS 发布需另行准备 macOS 构建环境、签名和真机验证。

## 11. 开发顺序

1. **设计确认**：审核本稿与双窗口原型，确定日期含义、父子规则与样式。
2. **技术样机**：验证 Windows 原生透明、置顶、拖动、穿透恢复、双窗口通信、离线安装。
3. **领域与数据**：完成日期不变量、事件事务、SQLite 迁移、备份恢复及关键规则测试。
4. **首版功能**：连接客户端与浮窗，完成 P0 和必要错误/空状态。
5. **打包验收**：断网、重启、跨日、并发、显示器切换和备份恢复测试。
6. **后续**：工时、月历、重复任务、iOS 本地客户端；同步作为单独项目设计。

## 12. 当前实现与边界（v0.3.0）

已交付 Windows x64 离线安装版与浏览器设计原型。支持任务区间、首次实际开始锁定、延期历史、子任务、月历与甘特图、常见公历周期及农历月 / 年周期、项目名称配色与排序、任务置顶与排序、悬浮窗项目筛选、SQLite 和 JSON 备份恢复、托盘、自启动、浅色 / 深色外观。

浏览器原型固定演示日期为 2026-10-20，数据保存在 localStorage；安装版使用本机日期、SQLite 与独立透明窗口。iOS、云同步、工时计时、独立子任务日期与归档尚未实现。

## 13. v0.3.0 需求及验收

1. 农历周期：新增月 / 年安排、月日选择和闰月策略；日期旁显示农历。三十遇小月取廿九，次个大月恢复；仅闰月的无对应年份跳过，不伪造日期。支持 1900–2100 年；每期仍独立记录，公历与农历不漂移。保存公历日期、农历规则和期次标识，旧公历规则兼容。
2. 项目自定义：新建 / 双击或编辑按钮修改名称与颜色；长按拖动改变顺序。更名须在同一事务迁移任务与周期归属，并为任务追加更名足迹，不改已有事件、首次开始或最初计划。
3. 浮窗项目筛选：下拉全部 / 单项目，进度、清单、缩略轮播共用筛选，持久保存且随更名更新。
4. 日历连续时间条：同任务每周内合并跨日显示，跨周裁剪续接；不同任务重叠时分配独立行，默认最多五行，可展开本周所有事项。完成为绿色，项目自定义色用于未完成事项。
5. 任务置顶：主列表、浮窗、详情、日历与甘特图提供图钉开关；最新置顶进入置顶组首位，多个置顶任务可再排序。窗口始终置顶开关独立。
6. 拖动排序：菜单、项目、任务长按约 380ms 激活，普通单击 / 双击保留原功能。菜单、项目各自排序；任务同完成 / 置顶组内排序，全局共用，不更改任务日期。指示线、Esc 取消、Alt + 方向键备用操作。持久顺序在重启、备份恢复与两个窗口间一致。
7. 数据兼容：旧 schema 1 无显示设置时采用默认值；项目列表省略时不丢弃已有空项目；改名不允许覆盖已有项目或遗漏任务；单任务导出仅保留自身排序 ID，周期副本停止重复。

技术：内置 [lunar-javascript](https://github.com/6tail/lunar-javascript) 1.7.7，MIT 许可保留在 prototype/vendor。换算不联网。领域测试覆盖春节、闰六月、小月、结束日期、离线补齐、跨周条、原子更名、排序保存和旧格式。


## 14. v0.4.0 右键操作与恢复

分区、任务、子任务提供同主题右键菜单；子任务可改名并记录旧 / 新名称。删除使用 deletedAt 软删除，事件继续只追加；子任务数组保留已删除记录，正常视图、日历、甘特图、浮窗、统计与完成校验只处理可见记录。回收站可恢复三类内容，提供搜索；单组超过 100 条可检索。

分区保留注册名称与颜色，preferences.projectTrash 保存删除模式和目标分区。迁移模式在同一事务更新全部所属任务及周期模板，任务追加 project_move 足迹；连带删除则软删除任务并停止所属周期。恢复原分区不逆转迁移，恢复连带删除仅找回当时随之删除的任务，不覆盖此前单独删除的任务，不重启已停止周期。最后一个分区删除后创建可用的“未分区”。

## 15. v0.4.1 任务右键切换业务分类

业务分类沿用现有分区：任务菜单的「移动到分区」展开二级列表，按分区顺序显示有效分区、颜色与当前归属勾选；悬停、点击、方向键均可展开。单次选择只迁移该任务，子任务跟随；追加 project_move 的 fromProject / toProject 足迹，保留首次开始、所有计划、完成状态、置顶、顺序和既有历史。周期实例仅移动本期，其余实例和模板保持归属。客户端和悬浮窗同步更新分区计数、筛选与颜色。

菜单靠右向左展开，窄窗口必要时调整一级菜单位置以容纳两列；长名称截断并提供完整提示。已删除分区不提供为目标，目标失效或多窗口版本冲突时提示重新操作。

## 16. v0.4.2 回收站永久删除与可持续关闭

回收站包含逐项彻底删除和全量清空，先显示准确范围与计数，再确认执行；搜索不限制全量清空范围，空列表禁用清空。确认默认选中取消。主存储提供独立 purge(request, expectedVersion) 事务，仅读取已删除对象；正常提交仍限制历史只追加、首次开始与最初计划不变。并发版本变化拒绝执行，要求重新确认。

彻底删除任务移除任务、子任务和 events 行；彻底删除子任务移除子项，父任务原足迹保留并追加匿名清除记录。分区清除关联仍在其内的已删除任务与无引用停止周期，保留已经迁出的正常任务；仍被迁出任务引用的停止周期移到有效分区保留来源。其他回收站分区指向被清除目标时更新关联并标记 targetPurged，仍可恢复空分区。

周期模板可包含 excludedDates；只由永久删除事务追加，正常写入不可移除或覆盖。生成跳过已清除日期，继续寻找下一可用期次；备份 / 恢复与旧 schema 1 格式兼容。旧备份和已导出文件不会自动清除，确认窗口明确说明。

设置和回收站使用 scroll-dialog：标题和关闭按钮不参与滚动，只有 dialog-body 滚动。回收站底部关闭按钮同样固定。浅深两种主题、820 / 700px 窗口均需在内容滚到底部后确认关闭按钮坐标稳定、未被遮挡且可直接点击。

SQLite 校验拒绝未经足迹记录的删除 / 恢复 / 子任务改名，拒绝直接移除任务和子任务历史；首次开始与最初计划仍受原有约束。旧备份没有删除元数据时沿用可见状态。JSON 备份和原生双窗口同步包含回收站数据。

开始日期选择若超过已填写的完成日期，界面将完成日期同步到同一天；其他日期校验保持有效，调整计划仍在保存时追加审计事件。
