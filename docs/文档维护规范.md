# ToZ 文档维护规范

## 同步时机

文档同步是开发交付的一部分：每轮任务在实现、验证后且提交前，对照下表更新相关文档，并与对应代码在同一轮提交。它不是后台文件监听器，不会在每次保存源码时即时生成说明；只做本地提交也不等于已推送远程。

只有聊天回复或测试结果更新，而功能说明仍停留旧行为，不算同步完成。仍未实现的计划必须明确标注，不能因为写入需求就声称已经交付。

## 各文档的职责

| 文档 | 维护内容 | 必须更新的触发条件 |
| --- | --- | --- |
| [项目现状](项目现状.md) | 当前版本、已实现功能、数据契约、入口、待开发及验证边界 | 新能力、行为 / 架构 / 数据变化，已知限制解决或新增 |
| [开发需求文档](开发需求文档.md) | 业务规则、数据约束、验收目标和功能补充 | 需求变化、日期 / 周期 / 父子 / 删除语义改变 |
| [Windows 安装版说明](Windows安装版说明.md) | 当前用户操作、安装、设置、数据、备份、构建 | 菜单 / 设置 / 窗口行为、安装、启动、备份与构建流程改变 |
| [视觉与交互规范](视觉与交互规范.md) | 主题、颜色、布局、组件与交互细节 | 颜色、文字层级、交互入口、弹层、滚动、尺寸变化 |
| [验证记录](验证记录.md) | 按日期记录实际执行的检查、结果、限制与产物位置 | 完成测试 / 验收，或因环境未能验证；纯文档任务可记录文档校验 |
| [README](../README.md) | 快速入口、运行命令、主要功能和当前版本说明 | 新用户必须知道的入口、版本 / 构建方式或产品范围改变 |
| [AGENTS.md](../AGENTS.md)、项目技能 | 新会话读取路径、开发 / 提交约束 | 协作流程、目录结构或文档职责变化 |

小修复仍需判断受影响文档；例如修复一个现有按钮但没有改变其既定行为，可只记录实际验证，不为凑数量重复改写全部文档。确实不涉及说明变化时，在交付中说明原因。

## 提交前的同步检查

1. 列出本轮新增、改变、删除或修复的行为，以及涉及的字段、入口与平台。
2. 按上表选择对应文档；修正旧正文中的反向表述，而不只在末尾追加新章节。历史记录保留，但应清楚标注适用版本。
3. 当前版本以 `package.json` 为准；纯文档更新记录核对日期，不虚增客户端版本或生成没有功能变化的安装包。
4. 业务规则、实际代码和验收结果分开陈述。未执行的测试写“未运行”，不能复用上一版的测试数作为本轮成功结果。
5. 检查本地链接、文件路径与代码入口；说明被 `.gitignore` 排除的报告 / 截图 / 安装包在新克隆中不可用。不得写入真实任务或本机敏感数据。
6. 按自动提交技能审查暂存差异：代码与相关文档是否一起纳入。交付简述更新了哪些文档及实际验证结果，再报告本地提交；推送仍按明确授权执行。

## 新会话读取顺序

根目录规则 → 开发上下文技能 → 项目现状 → README / package.json → 对应功能文档与最新验证记录 → 相关源代码及测试。

如果文档与代码冲突，先核对用户当前要求、实际实现及较新的变更记录，明确现状与预期后修正文档或实现。不要把旧初稿自动解释为要在本轮补做的功能。
